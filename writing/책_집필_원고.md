## 1장. 서비스는 어떻게 만들어지는가?

### 학습 목표

완성할 서비스의 사용자 흐름을 설명하고, 프론트엔드·백엔드·데이터베이스·AI가 맡은 역할과 서로 연결되는 이유를 구분한다.

### 장 도입문

오늘 먹은 음식과 몸무게를 기록하는 서비스를 떠올려봅시다. 화면에서 날짜를 고르고 몸무게를 입력한 뒤 저장 버튼을 누르면 새로운 기록이 목록에 나타납니다. 브라우저를 닫았다가 다시 열어도 이전 기록을 확인할 수 있고, 다른 계정으로 로그인하면 그 사람의 기록이 보입니다. 사용자의 입장에서는 익숙한 기능이지만, 개발자의 입장에서 보면 몇 가지 질문이 생깁니다. 입력한 값은 어디로 전달되며, 기록은 어디에 남고, 서비스는 누구의 데이터를 보여줘야 하는지 어떻게 판단할까요?

이 책은 이러한 질문에 답하기 위해 하나의 작은 서비스를 처음부터 끝까지 만들어가는 과정을 다룹니다. 사용자가 보고 조작하는 화면, 요청을 받아 처리하는 API, 정보를 보관하는 데이터베이스를 차례로 살펴봅니다. 이후에는 음식의 칼로리를 추정하고 질문에 답하는 AI 기능을 연결합니다. 마지막으로 내 컴퓨터에서 실행하던 서비스를 인터넷을 통해 다른 사람도 사용할 수 있도록 배포합니다. 각 기술을 따로 외우기보다, 사용자의 행동 하나가 여러 구성 요소를 지나 결과로 돌아오는 과정을 이해하는 것이 목표입니다.

개발을 처음 시작하면 프레임워크나 라이브러리의 이름이 많아 무엇부터 배워야 할지 막막할 수 있습니다. 이 책에서는 기술의 이름보다 역할을 먼저 살펴보겠습니다. Next.js는 화면을 만드는 데, NestJS는 API를 구성하는 데 사용합니다. MySQL은 기록을 보관하고, AI는 기존 서비스가 처리하기 어려운 자연어 요청을 돕습니다. 처음부터 모든 기능과 문법을 알 필요는 없습니다. 지금 배우는 내용이 서비스의 어느 부분에 해당하는지 확인하고, 필요한 개념을 하나씩 연결하면 됩니다.

이 장에서는 아직 복잡한 코드를 작성하지 않습니다. 대신 앞으로 만들 서비스의 모습을 살펴보고, 사용자와 데이터가 이동하는 길을 그려봅니다. 이 그림은 뒤의 장에서 새로운 개념을 만날 때마다 현재 위치를 확인하는 안내도가 될 것입니다. 나중에 AI 코딩 도구를 사용하더라도 어떤 파일을 바꾸고 어떤 결과를 확인해야 하는지 판단하려면 이러한 전체 구조가 필요합니다. 먼저 우리가 만들 서비스에서 사용자가 무엇을 할 수 있어야 하는지부터 차근차근 정리해보겠습니다.

### 세부 아웃라인

#### 1.1 우리가 만들 서비스 소개

몸무게와 음식 기록이라는 익숙한 소재로 서비스의 목적을 소개한다. 회원가입과 로그인, 기록의 등록·조회·수정·삭제, AI 칼로리 추정, 채팅, 배포 후 재접속까지의 사용자 흐름을 보여준다. 기록 관리와 AI의 추정 기능을 구분하고, 이번 책에서 구현할 범위를 정리한다.

#### 1.2 서비스 전체 아키텍처

사용자가 저장 버튼을 누른 순간부터 결과를 확인하기까지의 과정을 설명한다. 브라우저, Next.js, NestJS, MySQL, AI 제공자의 역할을 배치하고 요청과 응답의 방향을 표시한다. 로컬 실행 구조와 배포 구조를 나란히 소개하되, 클라우드의 세부 설정은 7장으로 연결한다.

#### 1.3 프레임워크란 무엇인가?

반복되는 개발 작업과 공통 구조를 제공하는 도구로 프레임워크를 설명한다. 언어, 실행 환경, 라이브러리, 프레임워크를 구분하고 이번 프로젝트에서 각각의 예를 찾아본다. 프레임워크가 제공하는 부분과 개발자가 직접 결정해야 하는 서비스 규칙을 나누어 설명한다.

### 장 마무리

확인 질문: 몸무게를 저장하고 다시 조회할 때 어떤 구성 요소를 거치는가? 화면에 보이는 값과 데이터베이스에 저장된 값은 어떻게 연결되는가? AI 기능이 없어도 기록 서비스는 동작할 수 있는가?

다음 장 연결: 전체 구조를 이해했다면, 각 구성 요소를 내 컴퓨터에서 실행하기 위한 개발 환경과 기본 문법을 준비한다.

## 2장. 개발 환경과 기초 다지기

### 학습 목표

프로그램이 실행되는 위치와 과정을 이해하고, 이후 실습에 필요한 Node.js·TypeScript·프로젝트 폴더·Docker의 기본 개념을 익힌다.

### 장 도입문

서비스의 전체 모습을 살펴보았다면 이제 직접 만들어볼 준비를 해야 합니다. 개발 환경을 준비한다는 것은 필요한 프로그램을 설치하는 일만을 뜻하지 않습니다. 내가 작성한 파일이 어디에 있고, 어떤 프로그램이 그 파일을 읽어 실행하며, 실행 결과를 어디에서 확인하는지 알아야 합니다. 처음에는 터미널에 나타나는 경로나 오류 메시지가 낯설 수 있습니다. 하지만 현재 위치와 실행 중인 프로그램을 구분하는 습관을 들이면, 뒤에서 문제가 발생했을 때 원인을 찾는 일이 훨씬 쉬워집니다.

이번 프로젝트에서는 TypeScript로 화면과 API의 코드를 작성하고, Node.js를 활용해 개발 도구와 서버 프로그램을 실행합니다. 브라우저에서 실행되는 코드와 서버에서 실행되는 코드는 사용하는 언어가 비슷해도 역할과 접근할 수 있는 대상이 다릅니다. 따라서 문법을 배우는 것과 함께 코드가 실행되는 위치를 이해해야 합니다. 터미널에서 실행한 서버를 종료하면 왜 요청을 처리할 수 없는지, 소스 파일을 수정한 내용은 어떤 과정을 거쳐 반영되는지부터 살펴보겠습니다.

TypeScript는 데이터를 어떤 형태로 다룰지 코드에 표현할 수 있게 해줍니다. 음식 이름은 문자열이고, 몸무게는 숫자이며, 여러 기록을 모아두면 배열이 됩니다. 함수는 입력을 받아 필요한 처리를 수행하고 결과를 돌려줍니다. 이 장에서는 이러한 기본 개념을 앞으로 만들 서비스의 데이터와 연결해 배웁니다. 모든 문법을 한 번에 익히기보다는 음식 한 건과 몸무게 기록 하나를 표현하고 읽을 수 있는 수준부터 시작합니다. 파일을 나누고 서로 필요한 기능을 가져오는 방법도 같은 맥락에서 살펴봅니다.

데이터베이스와 AI 실행 환경에는 Docker를 사용합니다. 여기서는 복잡한 컨테이너 운영 기술보다, 필요한 프로그램을 일정한 설정으로 실행하고 상태를 확인하는 방법에 집중합니다. 내 컴퓨터의 프로그램과 컨테이너 안의 프로그램이 어떻게 연결되는지도 함께 이해합니다. 이 장을 마치면 프로젝트의 폴더를 찾아 이동하고, 필요한 프로그램을 실행하며, 문제가 생겼을 때 어느 창과 메시지를 확인해야 하는지 설명할 수 있게 됩니다. 이것이 이후의 실습을 스스로 이어갈 수 있는 기본 준비입니다.

### 세부 아웃라인

#### 2.1 Node.js 설치와 실행 흐름

Node.js의 역할과 브라우저 실행 환경의 차이를 설명한다. 터미널의 현재 폴더, 프로그램 실행과 종료, npm과 패키지, 프로젝트 스크립트의 의미를 익힌다. 설치 여부와 버전을 확인하는 이유, 개발 서버가 실행 중이어야 하는 이유, 오류 메시지를 읽는 기본 순서를 정리한다.

#### 2.2 TypeScript 핵심 문법

음식명과 몸무게를 예로 문자열·숫자·불리언·배열·객체를 설명한다. 변수, 조건문, 반복문, 함수, 타입과 인터페이스, 선택적 속성, 가져오기와 내보내기를 연결한다. 비동기 작업과 기다림의 의미를 소개하고, 타입 표기만으로 외부 입력이 검증되지는 않는다는 점을 짚는다.

#### 2.3 프로젝트 구조 이해

frontend와 backend를 분리한 이유와 주요 폴더의 역할을 설명한다. 소스 파일, 패키지 목록, 설치된 의존성, 환경변수, 빌드 결과를 구분한다. 프론트엔드와 백엔드를 서로 다른 터미널에서 실행하는 상황을 보여주고, 어느 폴더에서 작업하는지 확인하는 습관을 만든다.

#### 2.4 Docker와 컨테이너 이해

이미지, 컨테이너, 포트 연결, 볼륨을 MySQL과 Ollama 실행에 필요한 범위로 설명한다. 컨테이너의 실행·중지와 데이터의 보존은 서로 다른 문제임을 구분한다. Docker Compose의 역할을 소개하고, 상태와 로그를 확인하는 절차를 다음 장의 데이터베이스 실습과 연결한다.

### 장 마무리

확인 질문: 소스 파일과 실행 중인 프로그램은 어떻게 다른가? frontend와 backend의 실행 위치를 어떻게 구분하는가? 컨테이너를 중지한 것과 저장 데이터를 삭제한 것은 어떤 차이가 있는가?

다음 장 연결: 준비한 환경에서 MySQL을 실행하고, 서비스가 보관할 데이터를 실제 구조로 설계한다.

## 3장. 데이터베이스 설계

### 학습 목표

User·Weight·Food의 데이터와 관계를 설명하고, 테이블·기본키·외래키·데이터 타입을 서비스의 저장 요구와 연결한다.

### 장 도입문

화면에 입력한 몸무게가 잠시 보이는 것과, 다음 날 다시 접속해도 기록을 확인할 수 있는 것은 다른 일입니다. 서비스가 정보를 계속 기억하려면 화면 밖에 데이터를 보관할 장소가 필요합니다. 또한 여러 사람이 같은 서비스를 이용한다면 기록을 저장하는 것만으로는 충분하지 않습니다. 어떤 사용자가 남긴 기록인지 구분하고, 날짜에 따라 찾아보며, 수정하거나 삭제할 대상을 정확하게 선택할 수 있어야 합니다. 이 장에서는 이러한 요구를 데이터베이스의 구조로 옮겨봅니다.

데이터베이스 설계는 먼저 서비스가 기억해야 할 사실을 정리하는 데서 시작합니다. 사용자를 식별할 정보, 몸무게의 값과 기록 날짜, 음식의 이름과 칼로리와 섭취 날짜가 그 예입니다. 같은 종류의 기록은 일정한 형식으로 모아두고, 각각의 기록을 구별할 기준을 정합니다. 일상에서 표로 정보를 정리하는 경험을 떠올리면 출발하기 쉽습니다. 다만 서비스의 데이터는 단순한 표를 넘어 서로 관계를 가지며, 잘못된 연결이나 값이 들어가지 않도록 기준이 필요합니다.

우리가 만들 서비스에서는 한 사용자가 여러 개의 몸무게 기록과 음식 기록을 가집니다. 이 관계를 이해하면 왜 기록마다 사용자와 연결되는 값이 필요한지 알 수 있습니다. 사용자의 이름이나 이메일을 모든 기록에 반복해서 적는 대신, 사용자를 가리키는 식별자를 연결하는 이유도 살펴봅니다. 숫자와 문자열, 날짜를 구분하는 이유는 저장 공간의 문제에만 있지 않습니다. 어떤 값을 받아야 하고 어떻게 비교하거나 표시해야 하는지에도 영향을 주므로 서비스의 실제 사용 방식과 함께 결정해야 합니다.

이번 장에서는 MySQL에 접속해 테이블과 데이터를 살펴보고, 서비스의 관계를 ERD로 정리합니다. ERD는 어려운 기호를 외우기 위한 그림이 아니라, 어떤 데이터가 누구와 연결되는지 함께 확인하는 설계도입니다. 이후 API를 만들 때는 이 설계가 코드의 Entity와 저장·조회 작업으로 이어집니다. 지금 정한 이름과 관계가 다음 장에서도 그대로 연결되어야 독자가 데이터의 이동을 추적할 수 있습니다. 먼저 사용자가 서비스를 떠났다가 돌아왔을 때 무엇을 다시 보여줘야 하는지부터 생각해보겠습니다.

### 세부 아웃라인

#### 3.1 데이터베이스 기초 개념

데이터베이스와 DBMS, 테이블과 행·열을 기록 서비스에 대입한다. 기본키, 외래키, 관계의 의미를 설명하고 숫자·문자열·날짜 타입을 비교한다. CRUD와 SQL의 역할을 소개하며, 입력값의 조건과 저장 구조를 함께 설계해야 하는 이유를 정리한다.

#### 3.2 MySQL 도커 설치 및 실습

MySQL 컨테이너의 실행 여부와 접속 정보를 확인하는 흐름을 설명한다. 호스트, 포트, 사용자, 비밀번호, 데이터베이스 이름을 구분한다. 데이터베이스와 테이블을 살펴보고 기록을 저장·조회하는 실습을 설계하며, 접속 실패와 데이터 보존 여부를 확인하는 절차를 포함한다.

#### 3.3 서비스 ERD 설계

User·Weight·Food에 필요한 속성과 사용자 한 명이 여러 기록을 가지는 관계를 정리한다. 단위, 날짜, 필수 입력, 식별자, 삭제 시 연관 기록의 처리 원칙을 결정한다. ERD의 이름과 다음 장 Entity의 이름을 대응시키고, ORM이 이 관계를 코드로 표현하는 역할을 예고한다.

## 4장. API 만들기

### 학습 목표

HTTP 요청과 응답, Controller와 Service의 역할, 로그인과 JWT 인증, 사용자별 CRUD와 소유권 검증을 하나의 흐름으로 설명한다.

### 장 도입문

데이터베이스에 정보를 저장할 수 있게 되었다고 해서 곧바로 웹서비스가 완성되는 것은 아닙니다. 사용자의 브라우저가 데이터베이스의 비밀번호를 알고 직접 기록을 바꾸도록 만들 수는 없습니다. 입력값이 올바른지 확인하고, 요청한 사람이 누구인지 판단하며, 그 사람이 접근할 수 있는 데이터만 처리하는 중간 단계가 필요합니다. 우리가 만들 API가 그 역할을 맡습니다. API는 화면과 데이터베이스 사이에서 요청을 해석하고 서비스의 규칙에 따라 결과를 돌려주는 접점입니다.

이 장에서는 몸무게를 등록하거나 음식 목록을 조회하는 행동을 HTTP 요청으로 표현해봅니다. 요청에는 무엇을 하려는지, 어떤 데이터를 대상으로 하는지, 처리에 필요한 값이 무엇인지가 담깁니다. 서버는 요청을 처리한 뒤 결과와 상태를 응답합니다. 성공한 요청과 잘못된 요청을 구분할 수 있어야 화면도 적절한 안내를 보여줄 수 있습니다. 따라서 API를 만든다는 것은 주소를 정하는 것뿐 아니라 입력과 출력, 성공과 실패의 약속을 함께 만드는 일입니다.

NestJS에서는 요청을 받는 부분과 실제 처리 과정을 나누어 구성합니다. Controller가 요청의 입구라면 Service는 저장과 조회 같은 작업을 연결하는 중심입니다. 앞 장에서 설계한 데이터는 Entity와 데이터베이스 작업으로 이어집니다. 여기에 로그인과 인증이 더해지면 요청이 어느 사용자의 것인지 알 수 있습니다. 다만 로그인한 사용자라는 사실만으로 모든 기록에 접근할 수 있는 것은 아닙니다. 요청한 기록이 그 사용자의 소유인지 확인하는 과정도 필요하며, 이 구분을 CRUD와 함께 살펴보겠습니다.

화면을 만들기 전에도 API는 직접 호출해 확인할 수 있습니다. 이 장에서는 Swagger를 통해 요청을 보내고 응답을 살펴보며, 등록한 기록이 실제로 저장되었는지 확인합니다. 올바른 값뿐 아니라 잘못된 값과 다른 사용자의 기록에 대한 요청도 시험해봅니다. 몸무게 CRUD에서 전체 흐름을 자세히 익힌 뒤 음식 CRUD에 같은 원리를 적용합니다. 각 기능을 완성할 때마다 요청이 어디까지 도달했고 어떤 결과를 돌려주었는지 확인하는 습관을 함께 익혀보겠습니다.

### 세부 아웃라인

#### 4.1 RESTful API 기초 개념

리소스, URL, HTTP 메서드, 요청 본문, JSON, 상태 코드의 역할을 설명한다. 몸무게와 음식 CRUD를 요청과 응답의 약속으로 정리하고, 성공 응답과 입력 오류 응답을 구분한다.

#### 4.2 NestJS 구조 이해

Module·Controller·Service·DTO·Entity의 역할을 요청 하나의 이동 순서로 연결한다. 필요한 기능을 전달받는 의존성 주입과 ORM Repository를 입문 수준에서 설명하고, SQL과 저장·조회 코드의 관계를 짚는다.

#### 4.3 Swagger로 API 확인하기

문서에서 요청 항목과 응답을 읽고 직접 호출하는 방법을 설명한다. 인증 정보의 입력 위치와 실제 응답 확인을 포함하며, 문서에 적힌 계약과 서버가 반환한 결과를 비교하는 습관을 만든다.

#### 4.4 로그인 API 만들기

회원가입을 로그인에 필요한 선행 흐름으로 포함한다. 비밀번호 해시, 계정 확인, JWT 발급과 전달의 역할을 설명하고, 비밀번호를 응답에 넣지 않는 이유와 로그인 실패 처리 기준을 정리한다.

#### 4.5 몸무게 CRUD 만들기

인증된 사용자를 기준으로 기록을 등록·조회·수정·삭제하는 흐름을 설명한다. 입력 검증, 날짜와 단위, 응답 형태, 다른 사용자 기록에 대한 접근 거부를 확인한다. 인증의 내부 구조는 4.7에서 자세히 다룬다고 연결한다.

#### 4.6 음식 CRUD 만들기

몸무게 CRUD와 같은 처리 구조를 음식 데이터에 적용한다. 음식명, 칼로리, 섭취 날짜의 검증 조건과 공통점·차이점을 비교한다. 이번 장은 사용자가 입력한 기록을 저장하며 AI 추정은 6장에서 연결함을 명확히 한다.

#### 4.7 인증 미들웨어 만들기: JWT Guard와 소유권 검사

원안의 인증 절을 NestJS 구현에 맞게 구체화한다. 미들웨어와 Guard를 구분하고 토큰 검증, 사용자 식별, 리소스 소유권 검사의 차이를 설명한다. 토큰 없음·만료·타 사용자 접근 사례로 보호 동작을 검증한다.

확인 질문: 인증에 성공한 사용자라도 거부해야 하는 요청은 무엇인가? 입력 오류와 서버 오류를 어떻게 구분하는가? Swagger의 요청·응답과 데이터베이스의 실제 기록이 일치하는가?

다음 장 연결: 직접 호출해 확인한 API를 웹 화면에 연결하여 사용자가 폼과 버튼으로 기록을 관리하게 한다.

## 5장. 웹서비스 만들기

### 학습 목표

사용자의 입력이 API 요청으로 바뀌고 응답이 화면 상태에 반영되는 과정을 이해하며, 로그인과 기록 관리 화면의 정상·로딩·오류·빈 상태를 설계한다.

### 장 도입문

앞 장에서는 API에 직접 요청을 보내 사용자를 확인하고 기록을 저장했습니다. 이제는 개발 도구에 익숙하지 않은 사람도 같은 기능을 사용할 수 있도록 화면을 만들 차례입니다. 사용자는 요청 주소나 JSON의 형식을 몰라도 음식 이름을 입력하고 저장 버튼을 누를 수 있어야 합니다. 목록을 보고 잘못된 기록을 수정하거나 삭제할 수 있어야 하며, 문제가 생겼다면 무엇을 다시 확인해야 하는지도 안내받아야 합니다. 웹 화면은 이러한 사용자 행동을 서버의 기능과 연결하는 역할을 합니다.

화면을 만드는 일에는 글자와 버튼을 배치하는 것 이상의 판단이 필요합니다. 사용자가 입력 중인 값은 어디에 두고, 서버의 응답을 기다리는 동안에는 무엇을 보여줘야 할까요? 저장이 끝난 뒤 입력란을 비울지, 목록을 다시 불러올지도 결정해야 합니다. 아직 기록이 없는 경우와 서버에 연결하지 못한 경우는 화면이 비어 보인다는 점에서는 비슷하지만 의미가 다릅니다. 이 장에서는 성공한 장면뿐 아니라 로딩, 빈 목록, 오류가 발생한 장면까지 서비스의 동작으로 함께 다룹니다.

Next.js로 화면을 구성하면서 React의 컴포넌트와 상태, 이벤트라는 기본 개념을 익힙니다. 컴포넌트는 화면을 이해하기 쉬운 단위로 나누고, 상태는 입력값이나 조회한 기록처럼 화면에 필요한 정보를 담습니다. 사용자의 클릭과 입력은 이벤트가 되어 API 호출로 이어집니다. 처음부터 복잡한 화면 구조를 만들기보다는 로그인과 몸무게 기록이라는 익숙한 흐름을 먼저 완성합니다. 그다음 음식 기록 화면에서 같은 구조를 다시 적용하며 어떤 부분이 공통이고 어떤 부분이 달라지는지 확인합니다.

로그인 이후의 화면은 인증 정보와도 연결됩니다. 하지만 화면에서 버튼을 숨기거나 로그인 페이지로 이동시키는 것만으로 데이터를 보호할 수 있는 것은 아닙니다. 실제 요청을 허용할지는 앞 장에서 만든 백엔드가 판단해야 합니다. 프론트엔드는 그 결과를 받아 사용자가 이해할 수 있는 화면으로 바꿉니다. 이 장을 마칠 때에는 버튼을 누른 순간부터 API 응답이 목록에 반영될 때까지의 흐름을 직접 따라가볼 수 있어야 합니다. 우리가 만든 서비스가 처음으로 사용자에게 익숙한 형태를 갖추는 과정입니다.

### 세부 아웃라인

#### 5.1 Next.js 구조 이해

페이지와 경로, 레이아웃, 컴포넌트의 역할을 소개한다. 화면 구현에 필요한 JSX·상태·이벤트·폼·비동기 요청을 함께 설명한다. 브라우저에서 실행되는 부분과 서버에서 처리되는 부분을 구분하고, 프론트엔드는 NestJS의 API를 호출한다는 기본 경계를 유지한다.

#### 5.2 로그인 화면 구현

회원가입과 로그인 폼, 입력 중인 값, 제출 중 상태, 실패 안내, 로그인 후 이동을 설계한다. 인증 정보의 저장과 API 요청에 담는 과정, 로그아웃, 만료된 인증의 처리 원칙을 설명한다. 화면 접근 제어와 서버의 실제 권한 검증이 다르다는 점을 다시 확인한다.

#### 5.3 몸무게 및 음식 CRUD 화면 구현

목록 조회, 등록 폼, 수정 상태, 삭제 확인과 결과 반영을 사용자 행동 순서로 구성한다. 공통 API 함수의 역할과 실제 JSON 응답을 화면 타입에 맞추는 과정을 설명한다. 로딩·빈 상태·오류·중복 제출·날짜 표시를 함께 다루고, 새로고침 후 저장된 기록을 다시 확인한다.

### 장 마무리

확인 질문: 입력란의 값과 서버에 저장된 값은 언제 같아지는가? 삭제가 성공한 뒤 화면에서 해야 할 일은 무엇인가? 로그인 화면으로 이동시키는 것만으로 데이터 접근을 막을 수 있는가?

다음 장 연결: 화면과 API, 데이터베이스가 연결된 기록 서비스에 자연어를 처리하는 AI 기능을 추가한다.

## 6장. AI 프롬프트 엔지니어링과 LLM 채팅

### 학습 목표

LLM 호출과 RAG의 차이를 이해하고, AI를 백엔드에 연결해 칼로리 추정과 채팅을 제공할 때 필요한 입력·응답·오류 처리 기준을 설명한다.

### 장 도입문

음식 기록을 남기다 보면 음식의 이름은 알지만 칼로리를 어떻게 입력해야 할지 막막할 수 있습니다. 사용자가 적은 음식 정보를 바탕으로 대략적인 값을 제안해주는 기능이 있다면 기록을 시작하는 데 도움이 될 것입니다. 또 서비스에서 궁금한 내용을 자연어로 묻고 답을 받을 수도 있습니다. 이처럼 정해진 버튼과 숫자 입력을 넘어 사람의 문장을 다루는 기능을 만들 때 LLM을 활용할 수 있습니다. 이 장에서는 이미 완성한 기록 서비스에 AI를 하나의 기능으로 연결해봅니다.

AI를 연결한다고 해서 기존의 화면과 API 구조가 사라지는 것은 아닙니다. 사용자는 화면에 음식명이나 질문을 입력하고, 프론트엔드는 백엔드에 요청을 보냅니다. 백엔드는 필요한 정보를 정리해 AI 제공자에게 전달한 뒤 응답을 받아 화면에 돌려줍니다. 이 과정에서 데이터베이스와 AI는 서로 다른 역할을 맡습니다. 데이터베이스가 저장된 기록을 정해진 조건으로 조회하는 반면, AI는 주어진 입력과 문맥을 바탕으로 응답을 생성합니다. 따라서 AI가 돌려준 값을 저장된 사실과 같은 수준으로 취급해서는 안 됩니다.

AI 기능을 개발할 때는 좋은 질문을 작성하는 것과 결과를 안전하게 다루는 것이 모두 필요합니다. 음식의 양이 빠지거나 조리법이 달라지면 칼로리 추정도 달라질 수 있습니다. 원하는 형식을 요청해도 응답이 그 형식을 따르지 않을 수 있고, 답변을 기다리던 중 연결이 끊길 수도 있습니다. 이 책의 칼로리 값은 교육용 추정 결과이며 정확한 영양정보를 보장하지 않습니다. 사용자가 이러한 한계를 알 수 있게 표시하고, 서버가 예상하지 못한 응답을 받았을 때 어떻게 처리할지도 함께 살펴보겠습니다.

이번 장에서는 Ollama로 모델을 실행하고, 관련 자료를 찾아 질문에 덧붙이는 간단한 RAG의 흐름을 이해합니다. 이어서 음식 칼로리를 구조화된 결과로 요청하는 방법과 채팅 화면을 연결하는 방법을 다룹니다. 검색한 자료와 사용자의 질문을 구분하고, 대화가 화면에 남는 것과 모델이 이전 대화를 전달받는 것은 다르다는 점도 확인합니다. AI가 그럴듯한 문장을 출력했다는 사실만으로 기능을 완성했다고 판단하지 않겠습니다. 서비스가 기대하는 결과와 실제 응답을 비교하는 과정까지가 이 장의 실습입니다.

### 세부 아웃라인

#### 6.1 LLM과 RAG의 이해

입력과 문맥을 바탕으로 응답을 생성하는 LLM의 역할과 한계를 설명한다. 모델 호출, 프롬프트, 문맥, 검색 결과 주입을 구분한다. RAG는 관련 자료를 찾아 응답 생성에 활용하는 흐름이며, 검색을 붙여도 정확성이 자동으로 보장되지는 않음을 짚는다.

#### 6.2 Ollama 도커에 설치 및 실행

Ollama 서버의 실행과 사용할 모델의 준비를 구분한다. 컨테이너·포트·모델 이름·백엔드 연결 설정을 설명하고, 처음 응답을 기다리는 상황과 연결 실패를 확인하는 순서를 정리한다. 필요한 자원과 대기 시간은 실습 환경 검증 단계에서 안내한다.

#### 6.3 간단한 RAG 실습

작은 서비스 안내 자료를 준비하고 질문과 관련된 내용을 찾아 프롬프트에 포함하는 흐름을 설계한다. 검색 자료와 사용자 지시를 구분하고, 검색 결과가 없을 때의 동작도 다룬다. 검색 전후 답변을 비교하되, 복잡한 벡터 데이터베이스 도입은 필수로 두지 않는다.

#### 6.4 프롬프트 엔지니어링으로 음식 칼로리 예측 기능 구현

목차의 ‘예측’을 본문에서는 한계가 있는 ‘추정’으로 설명한다. 음식 정보, 응답 필드, 단위와 주의 문구를 정리하고 JSON 형태와 값의 타입·범위를 검증한다. 사용자에게 결과를 보여주는 흐름까지 설계하며, 음식 기록 저장과의 연결은 후속 집필에서 범위를 확정한다.

#### 6.5 LLM 채팅 기능 구현

메시지 입력, 전송, 응답 대기, 답변 표시와 실패 처리를 설명한다. 현재 샘플처럼 질문을 독립적으로 처리하는 방식을 기본으로 두고, 화면의 대화 목록과 모델에 전달하는 대화 문맥을 구분한다. 인증된 API를 거쳐 호출하며 AI 제공자 정보는 백엔드에 둔다.

### 장 마무리

확인 질문: RAG에서 검색한 자료는 어느 시점에 모델에 전달되는가? 올바른 JSON이라도 믿고 사용할 수 없는 값은 무엇인가? 화면에 이전 대화가 보이면 모델도 그 대화를 기억하고 있는가?

다음 장 연결: 로컬 AI를 호출하던 서비스를 외부 API와 배포 환경에 맞게 설정하고, 인터넷에서 접근 가능한 서비스로 옮긴다.

## 7장. 배포

### 학습 목표

로컬 환경과 배포 환경의 차이를 이해하고, 환경변수·비밀값·AI 제공자 전환·AWS 백엔드·Vercel 프론트엔드의 연결을 검증하는 순서를 정리한다.

### 장 도입문

내 컴퓨터에서 서비스를 실행하고 사용하는 데 성공했다면 이제 다른 사람도 접속할 수 있게 만들 차례입니다. 개발 중에는 프론트엔드와 백엔드, 데이터베이스가 가까운 곳에서 함께 실행되지만, 배포 후에는 서로 다른 환경에 놓일 수 있습니다. 그동안 사용하던 주소를 그대로 옮기는 것만으로는 연결되지 않는 이유도 여기에 있습니다. 사용자의 브라우저에서 접근할 주소, 백엔드가 데이터베이스에 연결할 주소, AI를 호출할 방법을 각각 확인해야 합니다. 배포는 프로그램을 올리는 일과 연결을 다시 확인하는 일을 함께 포함합니다.

이 장에서는 프론트엔드를 Vercel에, 백엔드를 AWS에 배포하는 흐름을 살펴봅니다. GitHub는 소스와 변경 이력을 관리하고 배포 과정과 연결하는 역할을 맡습니다. 각 서비스가 어디에서 실행되는지 구분하면 문제가 생겼을 때 확인할 위치도 분명해집니다. 화면은 열리지만 로그인이 되지 않는 경우, API는 응답하지만 데이터베이스에 저장되지 않는 경우, 기록 기능은 동작하지만 AI 요청만 실패하는 경우를 서로 나누어 볼 수 있습니다. 로컬에서 배운 요청의 흐름을 배포 환경에서도 같은 방식으로 따라가겠습니다.

환경이 달라져도 소스 코드를 매번 고쳐야 한다면 관리하기 어렵습니다. 서버 주소와 데이터베이스 접속 정보, AI 제공자와 비밀값을 환경변수로 구분하는 이유를 여기서 확인합니다. 다만 모든 환경변수가 비밀로 유지되는 것은 아닙니다. 브라우저에 전달되는 설정과 서버에서만 사용해야 하는 값을 나누고, 공개 저장소에 올려서는 안 되는 정보를 구별해야 합니다. 로컬 실습에서 편의를 위해 사용한 비밀번호나 설정을 배포 환경으로 그대로 가져가지 않도록 점검하는 과정도 필요합니다.

AI 호출은 로컬 Ollama에서 Gemini API로 전환하는 사례를 통해 환경별 차이를 살펴봅니다. 제공자가 바뀌더라도 화면이 사용하는 요청과 응답의 약속은 유지하는 것이 목표입니다. 배포를 마친 뒤에는 화면이 열린다는 사실만 확인하지 않고, 회원가입과 로그인, 기록 저장과 재조회, 수정과 삭제, AI 호출까지 직접 수행합니다. 재접속한 뒤에도 데이터가 남아 있는지 확인하고, 실습을 종료할 때 자원과 비용을 어떻게 정리할지도 살펴봅니다. 이렇게 해야 사용자가 실제로 이용할 수 있는 서비스로 연결되었다고 판단할 수 있습니다.

### 세부 아웃라인

#### 7.1 환경변수와 보안

개발·배포 환경의 주소와 설정을 구분하고 서버 전용 비밀값과 브라우저 공개 설정을 나눈다. HTTPS, CORS, 인증, 데이터 소유권이 각각 해결하는 문제를 구분한다. 운영 데이터베이스의 스키마 변경과 데이터 보존, 배포 전 비밀값 점검을 포함한다.

#### 7.2 AI 모델을 Ollama에서 Gemini로 바꾸기

Ollama 실행 환경과 Gemini API 호출 방식의 차이를 설명한다. 백엔드의 제공자 선택, 인증 정보, 모델 설정, 오류와 대기 시간 처리를 정리한다. 화면의 API 계약을 유지하는지 확인하며, 모델 지원 여부와 사용 조건은 실제 집필·실습 시점에 재검증한다.

#### 7.3 GitHub 연동해서 AWS에 API 서버 배포

소스 관리, 빌드, 실행, 로그 확인으로 이어지는 배포 흐름을 설명한다. 백엔드와 MySQL의 배치, 연결 주소, 포트, 비밀값, 저장 유지와 스키마 준비를 포함한다. 독자가 따라 할 AWS 배포 경로는 하나로 확정할 예정이며 이번 초안에서는 특정 상품을 확정하지 않는다.

#### 7.4 GitHub 연동해서 Vercel에 웹서비스 배포

프론트엔드 프로젝트 연결과 빌드 설정, 배포 API 주소의 적용을 설명한다. 백엔드와의 CORS 및 HTTPS 연결을 확인하고 실제 사용자 흐름을 처음부터 재현한다. 소스 변경 후 재배포, 저장된 기록 확인, 실습 자원 종료와 비용 확인까지 마무리 절차에 포함한다.

### 장 마무리

확인 질문: 배포된 프론트엔드가 호출해야 할 API 주소는 무엇인가? 브라우저에 노출되면 안 되는 정보는 어디에 두는가? 재배포한 뒤에도 기존 기록이 남아 있다는 것을 어떻게 확인하는가?

다음 장 연결: 완성한 서비스를 바탕으로 더 배우고 싶은 분야와 AI 코딩 도구를 활용할 때의 검증 습관을 정리한다.

## 8장. 이제 어디로 가야 할까

### 학습 목표

프론트엔드·백엔드·AI의 다음 학습 방향을 구분하고, 협업과 AI 코딩 도구 활용에서 요구되는 설명·변경 확인·실행 검증의 습관을 정리한다.

### 집필 메모

이 장은 원안에서 포함 여부를 고민 중인 장이다. 최종 수록 여부는 미정으로 유지한다. 초안은 새 기능을 대량으로 추가하지 않고, 앞서 완성한 경험을 정리하는 마무리 장으로 작성한다.

### 장 도입문

처음에는 저장 버튼 하나가 어떤 과정을 거쳐 기록을 남기는지 알기 어려웠을 것입니다. 이제는 화면의 입력이 API 요청으로 바뀌고, 백엔드가 사용자를 확인한 뒤 데이터베이스에 저장하며, 결과가 다시 화면에 반영되는 과정을 따라가보았습니다. AI에 질문을 전달하는 기능을 연결했고, 서로 다른 실행 환경에 놓인 구성 요소가 인터넷을 통해 동작하도록 배포하는 흐름도 살펴보았습니다. 책에서 다룬 서비스는 작지만, 하나의 기능을 끝까지 연결해보았다는 경험은 다음 프로젝트를 시작할 때 사용할 수 있는 기준이 됩니다.

책을 마쳤다고 해서 모든 기술을 익힌 것은 아닙니다. 프론트엔드에는 더 다양한 사용자 경험과 접근성의 문제가 있고, 백엔드에는 데이터 처리와 운영의 문제가 있습니다. AI 기능도 질문을 보내 답을 받는 것에서 나아가 검색의 품질과 응답의 신뢰성을 살펴볼 수 있습니다. 중요한 것은 이 모든 내용을 한꺼번에 배우려고 서두르지 않는 것입니다. 완성한 서비스를 사용하면서 어떤 부분을 더 잘 만들고 싶은지 찾고, 그 문제를 해결하는 데 필요한 내용을 선택하면 다음 학습의 방향이 구체적이 됩니다.

AI 코딩 도구를 활용할 때도 같은 기준을 적용할 수 있습니다. 원하는 결과를 설명하는 일은 시작점이지만, 생성된 코드가 어디에 놓이고 어떤 데이터에 영향을 주는지 확인하는 과정이 뒤따라야 합니다. 기록의 모양을 바꾸는 요청인지, API의 응답을 바꾸는 요청인지, 저장 구조를 바꾸는 요청인지에 따라 확인할 대상이 달라집니다. 도구가 작업을 완료했다고 알려주더라도 직접 실행하고 실패 상황을 살펴보아야 합니다. 앞선 장에서 반복한 요청 추적과 검증이 이러한 판단을 위한 바탕이 됩니다.

이번 장에서는 새로운 기능을 많이 추가하기보다 앞으로의 선택지를 정리합니다. 화면을 더 편리하게 만들고 싶은 사람, 서버와 데이터를 깊이 이해하고 싶은 사람, AI 응용 기능을 더 실험하고 싶은 사람이 각각 어떤 질문에서 출발할 수 있는지 살펴봅니다. 다른 사람과 함께 개발할 때 변경 이유와 확인 결과를 남기는 방법도 돌아봅니다. 혼자 서비스를 완성해본 경험이 협업과 새로운 프로젝트로 이어지려면, 자신이 한 일을 설명하고 다른 사람의 변경을 확인할 수 있어야 합니다. 이제 완성한 서비스를 다음 학습의 출발점으로 삼아보겠습니다.

### 세부 아웃라인

#### 8.1 프론트엔드 심화 방향

사용자 경험, 접근성, 반응형 화면, 상태 관리, 렌더링과 성능을 다음 질문으로 제시한다. 현재 기록 화면에서 사용자가 불편할 수 있는 상황을 찾아보고, 문제를 관찰한 뒤 필요한 기술을 선택하는 학습 방법을 설명한다.

#### 8.2 백엔드 심화 방향

데이터 정합성, 트랜잭션, 테스트, 스키마 변경, 로그, 백업과 운영을 연결한다. 단순히 기능이 실행되는 것에서 데이터와 서비스를 안정적으로 유지하는 것으로 관심을 넓힌다. 작은 프로젝트에도 적용할 수 있는 확인 습관과 이후의 전문 주제를 구분한다.

#### 8.3 AI 개발 방향

프롬프트와 검색 품질 개선, 응답 평가, 오류 분석, 비용과 지연 시간, 개인정보 취급을 학습 방향으로 정리한다. 한 번의 그럴듯한 답변보다 여러 질문에서 결과를 비교하는 태도를 강조하고, 서비스 개발과 모델 학습은 서로 다른 심화 경로임을 설명한다.

#### 8.4 실무 협업 구조

역할 분담, Git 변경 이력, 작업 설명, 코드 리뷰, 실행 결과 공유를 소개한다. AI 도구가 만든 변경도 사람이 만든 변경과 같이 검토해야 함을 설명한다. 요청 범위 정리, 변경 파일 확인, 실행·오류·보안 검증의 순서를 완성 서비스의 사례로 되짚는다.
